# Velora — Project Documentation

## Purpose

Velora is an AI-driven, multi-character roleplay chat engine. Characters converse with one another while roleplaying inside a living world; the user directs how the conversation flows and can also play as a character. A persistent **Narrator** describes the situation and environment alongside character dialogue, so the central chat reads like a scene rather than a flat message thread.

The story is driven by a multi-agent backend that emits **small, typed story events** — the AI generates validated events and the UI renders them; the AI never decides UI layout. A near-term **character stat system** (bounded, guided numeric values that shape outcomes) gives the world continuity and consequence. Dice-based resolution is treated as an optional later layer.

**Core domain objects:** Storyline, Character, Setting, Scenario — plus the **Story Event** abstraction and the **Stat** system.

- **Storyline** — the overarching world and its persistent truth; owns the baseline **stat schema** and holds its characters, settings, and scenarios.
- **Character** — a person in the storyline: descriptive (personality, speech, goals, secrets, relationships) and numeric (a stat block of current values).
- **Setting** — a place within the storyline, tracked over time (who's there, state, time/weather, features).
- **Scenario** — the live "truth object" for the present moment: active characters, turn order, goals, tone, world flags, and any scenario-specific stat additions/overrides. The model generates *from* this and emits events that *update* it.

## Architecture Summary

```
User Input → Orchestrator → Scenario State → Character/Narrator agents
→ Structured Event Output → Validator (incl. stat clamping) → Event Stream → Frontend Renderer
```

```
Frontend (Next.js/React/TS/Tailwind/Framer Motion)
        ↓  HTTP + SSE/WebSocket (NDJSON events)
Backend "Brain" (FastAPI): Orchestrator/Director · Narrator · Character · State manager · Validator
        ↓
Data: PostgreSQL (core) · Redis (live scenario) · Neo4j (Story Graph) · Qdrant (hybrid RAG)
        ↓
AI: LLMs (OpenAI / local) · multi-agent · YAML config + Markdown stat guidance injected per turn
```

The frontend and backend both live under `web/`; a thin root `app.py` runs the FastAPI backend. See `docs/architecture.md` for route/auth/data-flow detail, `docs/structure.md` for the layout, and `docs/design-system.md` for the visual language.

## Major Decisions

- **Domain model:** four canonical objects (Storyline / Character / Setting / Scenario) + a Story Event abstraction + a Stat system. Replaces the earlier flat "scene" model.
- **Event-driven rendering:** the AI emits small typed events; the backend validates them; the frontend maps each event type to a component. Start with **five** event types (`narration`, `character_dialogue`, `character_action`, `state_update`, `branch_choices`).
- **Stat system (near-term):** bounded numeric values defined on the storyline (and optionally tightened by a scenario), held per character, **clamped by the validator**, with a Markdown guidance file per stat injected into agent context. Relationship/mood values are the same object with a relational target.
- **Format split:** YAML for hand-authored config, Markdown for stat guidance, JSON/NDJSON for live streaming, JSON Schema/Zod for validation.
- **Repo layout:** "everything under `web/`" — `web/frontend` (Next.js) + `web/backend` (FastAPI) + `web/shared/contracts`. Root `app.py` is the backend entrypoint.
- **Python tooling:** `uv` only, Python 3.13.
- **Agent tools supported:** Claude Code, OpenAI Codex, Cursor. Canonical instructions live in `docs/skills/`; agent folders only point to them.
- **Git workflow:** commit per phase (no auto push/PR unless requested).
- **Validation gate:** pytest (backend) + frontend component/route tests; web/UI changes also require an accessibility + responsive pass.
- **Story Graph (Neo4j):** one knowledge graph on Neo4j 5.26 (custom container). Node `type` → label, edge `type` → relationship type, every node also `:Node` (§6.1); dynamic labels via bound params (§6.2); the **Type Registry** in Postgres is the semantic type system, Neo4j holds instances (§1.4); the consequence record is a reified `:Consequence` node (§6.4). Decided: **graceful/best-effort** (never blocks CRUD; optional preflight check; tests run with no Neo4j); **substrate + sync + template read** now, with the async turn-writer (§8), vector entry-point (§7.1), and Text2Cypher (§7.3) as seams; user-defined types **staged** (§10). See `docs/story-graph-neo4j.md`.
- **Hybrid RAG (fastembed + Qdrant):** embed-on-save with live reindex progress, hybrid dense + BM25 + RRF retrieval wired into the character / setting / scenario authoring agents, entity-scoped persistent context docs across all four editors (plus the edit-reload fix), delete-from-index on CRUD delete, best-effort / offline-testable (`EMBED_PROVIDER=hash`, no Qdrant needed). Cross-encoder rerank and Neo4j KG edges are deferred. See `docs/rag.md`.
- **Deferred capabilities:** dice-based resolution (optional later layer); cross-encoder rerank and Neo4j KG edges for the RAG layer.

The **"Build the whole world" doc-extraction stage is now parallel + fault-tolerant** (plan: `docs/plans/build-extract-stage-fix.md`), fixing a report where the build hung on "Reading Docs" and failed with `"The model did not return valid JSON."` on large (40+ file) uploads: extraction ran one LLM call **per doc sequentially**, emitted a single status for the whole loop, and let **any one** doc's malformed reply abort the entire build. It now mines every doc **concurrently** (bounded by `authoringConcurrency`, connection pre-resolved so workers never touch the request `Session`) at **LOW** reasoning effort (segmentation — faster, less JSON truncation), **retries a doc once then skips it** (named in a status line) instead of aborting, de-dups in **document order** (index slots, stable under out-of-order completion), and streams a **per-doc `extract` status** so the UI shows movement. The follow-up **RAG-first ingestion + native-tool-calling ReAct** redesign (ingest every uploaded doc into an *ephemeral build-scoped RAG namespace* first, then let the character/setting agents query it on demand during generation) is captured as a separate plan (`docs/plans/rag-first-ingestion.md`), not yet implemented. **Build extraction now respects the author's classification** (plan: `docs/plans/build-extraction-respect-classification.md`), fixing a report that the build *invented* characters/settings by "expanding context" from lore and mined even the docs the author explicitly classified: extraction is now **strict + named-only** (only explicitly named, genuinely-profiled subjects — never invented/inferred/expanded from lore/history/rules/terms; a name mentioned in passing is not a subject; a lore doc yields nothing) and **bucket-scoped** — `characterDocs` → named characters only (usually one; split only if clearly several; a classified doc with no explicit name still becomes **one**, never lost), `settingDocs` → named settings, the new **`uncategorizedDocs`** request field → strict named characters/settings or **nothing**, and **`otherDocs` → lore/grounding only** (never entities, folded into the drafting grounding). A new `kind` param scopes the extraction agent and clears the off-kind list; the frontend routes each triage bucket to its own list. **Play-experience fixes** (plan: `docs/plans/play-experience-narrator-thoughts-stats-graph.md`) then addressed four in-scene defects: (1) **narrator output is sanitized** — the one freeform-prose agent now runs its reply through `_common.strip_reasoning`, so a reasoning model's chain-of-thought + harmony channel tokens (`<|channel|>`, `*Check:*`/`*Revised:*`) no longer leak into the beat; (2) a character's hidden **thinking now folds into the same transcript beat as their speech** (a muted line between the name and the spoken bubble) instead of a separate bubble; (3) the **character dossier's stat sliders update live per character** — stats are now bucketed by `characterId` (`applyStatByChar`) and the sliders are value-aware, fixing a bug where the dossier always showed schema defaults; and (4) the Inspector's green **Graph** trace steps now list the real changes (`commit` names each `Consequence` summary; the first-turn `relationships` seed lists the edges written, via `ensure_seeded` returning per-edge summaries). **Persistent scene saving + conversation export** now ships (plan: `docs/plans/scene-saving-and-export.md`): every play-through is fully durable and reopenable. The **diagnostic trace is now persisted** to a new `turn_traces` table (keyed by `(session_id, turn, n)`) on **every** turn — independent of the opt-in *streaming* flag — so the knowledge-graph writes and the RAG/lore look-up that were previously transport-only survive for later review; `PlaySession` gained `updated_at`/`closed_at`. Reopening a scenario **resumes its most recent session** — `useScenePlay` loads the full history (`GET /play/{id}/sessions` → `.../sessions/{id}`) and `turn-stream.rehydrateFromHistory` **replays the persisted rows through the live reducers** to restore the transcript, thoughts, live stats, and Inspector trace, then continues on that session; leaving the scene fires `POST .../sessions/{id}/close` (`navigator.sendBeacon`) as the save-on-close signal. A new **Export** control in the scene header (left of the theme switcher — `ExportMenu`) downloads the complete conversation record via `GET .../sessions/{id}/export?format=json|md` (server-rendered by `services/session_export` from the persisted rows: turn-by-turn flow · character thoughts · graph + RAG activity), as structured **JSON** or human-readable **Markdown**.
