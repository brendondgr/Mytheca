# Plan — Context Documents Manager + Entity Doc Provenance

## 1. Introduction

Today, once a storyline exists, its uploaded context documents are effectively invisible: the only surface that lists them is the New/Edit Storyline page's Triage panel (storyline‑level docs only), and the Character/Setting editors show only the files dropped *inside that modal*. A world author with dozens of `.md` reference files has no way to see the full corpus, how each doc is used (Draft / RAG / Extract / scope), or which documents grounded a given character or setting. This plan closes both gaps.

The approach, within Mytheca's stack (Next.js frontend, FastAPI backend, Postgres + Qdrant RAG): (1) a **dedicated document‑manager route** `/storylines/[id]/documents` (new `features/documents/` module) that lists **every** `ContextDocument` for a world with its category, usage flags, scope, char‑count and linked entities, and lets the author adjust flags/category, upload, delete, and link/unlink docs to entities; and (2) **real doc→entity provenance** — a new many‑to‑many `ContextDocumentLink` layer, populated automatically at build time (recording which uploaded doc produced each character/setting) and editable manually, surfaced as a **"Source documents"** section on the right of the Character/Setting edit modals. The backend already scopes docs via `entity_type`/`entity_id` and filters on them; that "owned by the editor" concept is preserved unchanged — the new link layer is a *reference/provenance* relation that a doc can hold to several entities (and vice‑versa) without changing the doc's primary scope or its cascade‑delete behavior.

## 2. Gaps & Unanswered Questions

- **Doc manager location — RESOLVED (user):** a dedicated full‑page route `/storylines/[id]/documents` (not a Library drawer, not just the Edit page).
- **Entity provenance definition — RESOLVED (user):** record real lineage during **Build the whole world** *and* allow manual link/unlink from the modal.
- **Lineage cardinality (assumption):** a document can build/relate to **multiple** entities and an entity can draw from **multiple** docs → modeled as a **separate many‑to‑many link table** (`context_document_links`), *not* by overloading the existing single `entity_type`/`entity_id` scope (which would wrongly convert a corpus doc into an entity‑owned, cascade‑deleted doc and cap it at one entity). Manual linking never mutates the doc's own scope.
- **Provenance vs. ownership (assumption):** the Character/Setting modal keeps its existing **owned** context‑files column (`ContextFilesPanel`, docs scoped to the entity, embedded + cascade‑deleted) and gains a *separate* **Source documents** section for **links** (references into the storyline corpus, unlinking removes only the link, never the doc). These are two distinct concepts and are labeled as such.
- **RAG impact (assumption):** links are pure provenance metadata — they do **not** affect embeddings or retrieval, so no `rag/` changes.
- **Migration (assumption):** the new table is additive; a standard Alembic migration chained after the current head. No column changes to existing tables.
- **Build lineage timing (assumption):** the backend build only *proposes* (persists nothing); the commit is the frontend CRUD sequence (`storylineCreator.commitWorld`). So the backend's job is to **carry each proposed entity's source doc name(s)** on the proposal, and the frontend creates the links at commit (source doc name → persisted doc id → new entity id).

## 3. Hierarchical Step-by-Step Instructions

### Phase 1 — Backend: doc↔entity link model, schemas, CRUD & endpoints

- **Locations:** `web/backend/app/models/context_document.py` (new `ContextDocumentLink` model + relationship), `web/backend/alembic/versions/<new>.py` (additive `context_document_links` table, chained after current head), `web/backend/app/schemas/context_document.py` (`ContextDocumentLinkRead`, `ContextDocumentLinkCreate`; add `links: list[…]` to `ContextDocumentRead`), `web/backend/app/services/crud.py` (`add_document_link`, `remove_document_link`, `list_documents_linked_to_entity`, and fold links into `list_context_documents` reads + a `linked_entity_type`/`linked_entity_id` filter), `web/backend/app/routes/context_documents.py` (`POST /context-docs/{docId}/links`, `DELETE /context-docs/{docId}/links`, extend the list query with linked‑entity filter params). Update `core/bootstrap.py` reconciler expectations only if needed (new table is created by `create_all`).
- **Rationale:** The provenance relation is the foundation both the manager UI and the entity modal read; it must exist and be queryable before any frontend work. Modeling it as its own table keeps the doc's existing scope semantics intact.
- **Tests:** `utils/tests/backend/api/test_context_documents.py` (or the existing doc test file) + `utils/tests/backend/services/` — link create is idempotent (unique on `doc_id`+`entity_type`+`entity_id`), unlink removes only the link, list‑by‑linked‑entity returns the right docs, doc read includes its links, deleting a doc cascades its links, deleting the linked entity leaves the doc but the link is cleaned (or is filtered out on read — assert whichever the model enforces).
- **Action:** Run `uv run pytest utils/tests/backend`. Once green, commit: `[Context Documents Manager] (1/5) Complete: doc↔entity provenance link model, CRUD & endpoints.`

### Phase 2 — Backend: capture build-time source-doc lineage on the proposal

- **Locations:** `web/backend/app/schemas/build.py` (`ExtractedEntity.source_doc_names: list[str]`; `ProposedCharacter`/`ProposedSetting` gain `source_doc_names: list[str]`; ensure `BuildCharacterEvent`/`BuildSettingEvent`/`BuildDoneEvent` carry it through the existing `ProposedCharacter`/`ProposedSetting` payloads), `web/backend/app/agents/extract_agent.py` (stamp each `ExtractedEntity` with the doc it was mined from — `doc_name` is already in scope), `web/backend/app/agents/build_agent.py` (`iter_build_world` / the extract → cross‑doc‑dedup → draft pipeline: merge source doc names during de‑dup, carry them onto each drafted `ProposedCharacter`/`ProposedSetting`).
- **Rationale:** Extraction is the one place that knows which document produced which subject. Capturing it on the proposal is what lets the frontend commit create accurate links; nothing is persisted server‑side here (the build persists nothing by design).
- **Tests:** `utils/tests/backend/agents/` — an extracted entity carries its source doc name; a subject appearing in two docs merges both names after de‑dup; a drafted proposed character/setting surfaces `sourceDocNames`; the streamed character/setting events include it.
- **Action:** Run `uv run pytest utils/tests/backend/agents`. Once green, commit: `[Context Documents Manager] (2/5) Complete: build proposal carries per-entity source-document lineage.`

### Phase 3 — Frontend: link API/types + the `/documents` manager route

- **Locations:** `web/frontend/lib/types.ts` (`ContextDocumentLink`; add `links?` to `ContextDocument`; `sourceDocNames?` on the proposed‑entity types), `web/frontend/lib/api.ts` (`addDocumentLink`, `removeDocumentLink`, extend `listContextDocuments` scope arg with `linkedEntityType`/`linkedEntityId`), new `web/frontend/app/storylines/[id]/documents/page.tsx` (route), new `web/frontend/features/documents/` (`DocumentsView.tsx`, `useDocuments.ts`), new `web/frontend/components/feature/DocumentsTable.tsx` (rows: name, category `<select>`, Draft/RAG/Extract toggles, scope + linked‑entity chips, char‑count, view‑content, delete) + drag‑drop upload reusing `lib/readDocs.ts`. Entry point: add a **"Documents"** link/button in the Library storyline surface — `components/feature/StorylineMenu.tsx` or `components/layout/AppHeader.tsx` (whichever owns the active‑storyline chrome), routing to `/storylines/{id}/documents`.
- **Rationale:** This is the primary user‑visible gap (ask #1). It must list **all** docs (`listContextDocuments(id)` with no scope) with search/filter/grouping to scale to 50+ files, and edits go straight through the existing `updateContextDocument`/`deleteContextDocument`/`bulkCreateContextDocuments`.
- **Tests:** `web/frontend/features/documents/DocumentsView.test.tsx` + `components/feature/DocumentsTable.test.tsx` (renders all docs grouped, toggling a flag PATCHes, category change PATCHes, delete removes, upload creates, filter/search narrows); `lib/api.ts` mock additions in `test/api-mock.ts`; entry‑point test that the link navigates.
- **Action:** Run `cd web/frontend && npm test` (relevant suites) + `npm run typecheck && npm run lint`; accessibility/responsive pass (keyboard reachable rows/toggles, focus, contrast, 320/375/768/1024). Once green, commit: `[Context Documents Manager] (3/5) Complete: /documents manager route + link API/types + Library entry point.`

### Phase 4 — Frontend: entity-modal "Source documents" + wire build lineage at commit

- **Locations:** new `web/frontend/components/feature/SourceDocumentsPanel.tsx` (or a section inside the modals' right aside): lists docs **linked** to the entity (`listContextDocuments(sl,{linkedEntityType,linkedEntityId})`), each with an **unlink** control, plus a **"Link a document"** picker over the storyline corpus (`addDocumentLink`); wired into `components/feature/CharacterModal.tsx` and `components/feature/SettingModal.tsx` right asides. `web/frontend/features/library/useLibraryState.ts` (load an entity's linked docs when opening the modal; expose link/unlink handlers). `web/frontend/features/library/storylineCreator.ts` `commitWorld` (after creating each character/setting and persisting the corpus, resolve each proposed entity's `sourceDocNames` → the just‑created corpus doc ids → `addDocumentLink(docId,{entityType,entityId})`). `web/frontend/features/library/storylineCreator.ts` mappers keep `sourceDocNames` from the proposal.
- **Rationale:** Ask #2 — the author sees, on the right of the edit menu, exactly which documents were used as context for that character/setting (auto‑captured at build, plus anything they link manually), and can curate it. Commit‑time linking is where build lineage becomes durable, since the backend build persists nothing.
- **Tests:** `SourceDocumentsPanel.test.tsx` (renders linked docs, unlink calls API, picker links a corpus doc); `storylineCreator` commit test (a proposed character with `sourceDocNames:["maerin.md"]` produces an `addDocumentLink` to the created character id after the corpus is persisted); `useLibraryState` link/unlink handler tests.
- **Action:** Run `cd web/frontend && npm test` + `npm run typecheck && npm run lint`; accessibility/responsive pass on the new modal section. Once green, commit: `[Context Documents Manager] (4/5) Complete: entity Source-documents section + build-lineage links wired at commit.`

### Phase 5 — Docs, full validation & merge

- **Locations:** `docs/api-contract.md` (link endpoints + `links` on the doc read + `sourceDocNames` on proposed entities + build event note), `docs/data-flow.md` (Context Document Flow: provenance‑link layer, build lineage capture at commit, manager route read/write path), `docs/routes.md` (`/storylines/[id]/documents`), `docs/component-map.md` (`DocumentsView`/`DocumentsTable`/`SourceDocumentsPanel`/`useDocuments` + StorylineMenu entry), `docs/structure.md` (new `features/documents/` + `context_document_links` table + link model), `docs/documentation.md` (status), `docs/checklist.md` (this feature's Follow‑up entry), `CLAUDE.md` (component list). Run the **full** suites.
- **Rationale:** Docs‑in‑the‑same‑change is a non‑negotiable rule; the merge closes the plan.
- **Tests / validation:** full `uv run pytest`; `cd web/frontend && npm test && npm run typecheck && npm run lint && npm run build`; single Alembic head check; a11y/responsive pass recorded (or deferral documented in `checklist.md` if the live‑preview constraint applies).
- **Action:** Update all docs, run the full validation gate, commit: `[Context Documents Manager] (5/5) Complete: docs + full validation.` Then merge the worktree branch into `main`, resolving any conflicts and re‑running the gate.
