# Chat UX Additions — context bar, header Config, composer redesign, live scene pulse, character activity, type-while-streaming

## 1. Introduction

This plan modernizes the story-player chat experience in six user-visible ways: (1) an always-visible **context usage bar** showing estimated conversation tokens against the maximum context of the model currently in use (color-coded, hover shows `5K / 16K` style counts); (2) the **Config** button moves out of the composer into the `SceneHeader`, immediately **left of Export**, restyled to match the header buttons; (3) the **message input** becomes a single flowing panel — no background band, rounded top corners, an auto-growing textarea (≥5 lines visible as text grows), and a **circular Send button inside the input** on the right with a centered SVG that text wraps around; (4) the right rail's static goal/tension/relationships display is replaced by an **active, animated "Scene pulse" feed** of what is happening right now; (5) characters get **activity animations** — a typing indicator plus "Thinking"/"Speaking" status labels driven by the live turn stream; (6) the player can **keep typing while characters respond**, with only Send blocked until the turn finishes.

Approach within Velora's architecture: the backend gains one small capability — knowing the model's context window (auto-detected from the inference engine via the existing `llm_backend` detection seam: llama.cpp `/props` → `n_ctx`, vLLM `/v1/models` → `max_model_len`, with a configurable fallback stored in `app_settings` and editable in the Options LLM tab). Everything else is frontend: `contextBudget.ts` gains a transcript-usage estimator, `turn-stream.ts` gains an activity reducer (fed by the trace steps `useScenePlay` already requests), and `Composer` / `SceneHeader` / `DirectorRail` / `CastRail` are reworked. Work happens in the worktree `worktree-chat-ux-additions` (branch off `main`), commit per phase, merged to `main` at the end.

## 2. Gaps & Unanswered Questions

Assumptions taken (simple gaps — proceeding):

- **"Maximum context permitted by the model currently in use":** neither the settings store nor the LLM proxy tracks a context window today. Assumption: detect it from the running inference engine when possible (llama.cpp `/props`, vLLM `/v1/models`), else fall back to a new `max_context_tokens` setting (default **16384**) editable in Options → LLM. Detection is best-effort and cached like `llm_backend.get_backend`.
- **Usage numerator "based on the Number of Beats":** estimated tokens of the beats that will actually be sent as context — the last `min(contextBeats, messages.length)` transcript beats, summed with the existing `estimateTokens` char/4 heuristic over each beat's text + action + thought (more honest than the flat 180-char average, which stays for the config-menu slider estimate).
- **"Text wraps around the Send button":** a native `<textarea>` cannot flow text around a floated element; the standard modern-chat treatment is used instead — the textarea reserves a right padding column the width of the circular button, so text wraps before reaching it and never slides underneath. The button is absolutely positioned inside the panel, bottom-right.
- **"Include a text area to support this live display":** interpreted as a live-updating, scrollable text region (`role="log"`, `aria-live="polite"`) inside the right rail showing the feed of current happenings — not an editable form field.
- **Scene state chips stay:** the ask replaces the *static* goal / tension / relationships sections. The "Scene state" `StateChips` block is already live (driven by `state_update` events) and is kept beneath the new feed; stat changes also surface as feed entries.
- **Enter sends, Shift+Enter inserts a newline** in the new multi-line composer (standard chat convention).
- **Presence `<select>` and stat rows in `CastRail` are untouched** — "character profiles on the right side look fine and work as intended."

No complex gaps requiring human input were identified.

## 3. Hierarchical Step-by-Step Instructions

### Phase 1 — Backend: model context window (detect → configured fallback) + Options field

- **Locations:** `web/backend/app/services/llm_backend.py` (new `get_context_window(base_url, api_key) -> int | None`: llama.cpp `/props` → `default_generation_settings.n_ctx` (fallback top-level `n_ctx`), vLLM `/v1/models` → first model's `max_model_len`; unknown → `None`; cached per base_url like `get_backend`, reusing `get_http_client`); `web/backend/app/schemas/settings.py` (`LlmConfigRead.max_context_tokens: int = 16384`, `LlmConfigUpdate` counterpart, new `LlmContextWindowResponse{max_context_tokens: int, source: "detected" | "configured"}`); `web/backend/app/services/settings_store.py` (persist/read `max_context_tokens` in the `llm` namespace); `web/backend/app/routes/options.py` (new `GET /options/llm/context-window` → detected value when available, else the configured setting).
- **Frontend half:** `web/frontend/lib/api.ts` (`LlmConfig.maxContextTokens`, `LlmContextWindow` type, `getLlmContextWindow()` wrapper), `web/frontend/test/api-mock.ts` (mock), `web/frontend/features/options/tabs` LLM tab (numeric "Max context (tokens)" field with help text: used as fallback when the engine doesn't report one), `web/frontend/features/options/useOptionsSettings.ts` if save-shape changes.
- **Rationale:** the usage bar needs a denominator; nothing in the system knows the model's context limit today. Doing this first unblocks the bar and is independent of all UI phases.
- **Tests:** `utils/tests/backend/services/` — detection per engine + unknown fallback (injected httpx client, existing pattern); settings round-trip incl. default; `utils/tests/backend/api/` — endpoint returns detected vs. configured source. Frontend: options-tab field save test.
- **Action:** Run `uv run pytest` (settings/options/llm areas) + `npm test` (options) + typecheck. Once green, commit: `[Chat UX Additions] (1/7) Complete: model context window — engine detection + configurable fallback + Options field.`

### Phase 2 — Context usage bar in the chat

- **Locations:** `web/frontend/lib/contextBudget.ts` (new `estimateUsedTokens(texts: string[])`-style helper taking the last `contextBeats` beats' combined text, plus `fmtTokensK(n)` → `"5K"` / `"0.6K"` formatting); new `web/frontend/components/feature/ContextUsageBar.tsx` (slim full-width bar: `role="progressbar"` with `aria-valuenow/min/max` + `aria-valuetext="5K of 16K tokens"`, `title` tooltip with the same counts for hover, fill color by percentage — `bg-success`-style green < 50%, gold 50–75%, danger ≥ 75%, using existing theme tokens; width transition with `motion-reduce:transition-none`); `web/frontend/features/story-player/useScenePlay.ts` (fetch `getLlmContextWindow()` once on mount, best-effort; expose `contextWindow` + derived `usedTokens` from `messages` + `contextBeats`); `web/frontend/features/story-player/StoryPlayerView.tsx` (render the bar attached to the composer region so it lives "within the chat", directly above the input panel).
- **Rationale:** pure display work that depends only on Phase 1's endpoint; placing it with the composer keeps it visible without stealing transcript space.
- **Tests:** `contextBudget` unit tests (usage estimate, K formatting, boundary percentages); `ContextUsageBar.test.tsx` (green/yellow/red classes at <50/50–75/≥75, aria values, tooltip text `5K / 16K`); `useScenePlay` test — window fetched, fetch failure degrades (bar hidden or default max).
- **Action:** Run `npm test` (contextBudget, ContextUsageBar, useScenePlay, StoryPlayerView) + typecheck; a11y check: progressbar semantics, non-color text signal (the K counts), contrast of the three fill tokens. Once green, commit: `[Chat UX Additions] (2/7) Complete: color-coded context usage bar with hover token counts.`

### Phase 5 — Live activity state (turn-stream reducer + per-character status)

- **Locations:** `web/frontend/features/story-player/turn-stream.ts` (new `ActivityEntry {id, kind: "narration"|"thinking"|"speaking"|"action"|"stat"|"presence"|"plan"|"branch", who?, label, detail?, }` + reducer `applyActivity(list, frame)` mapping **trace steps** (`plan`, `speaker` → "X is about to speak", `thinking`, `dialogue`, `stat`, `presence`, `branch`) and **story events** (`state_update` → stat delta + reason, `character_status_change` → presence line, first `narration` chunk → "The narrator continues the scene") into a capped feed (latest ~12, newest first, stable ids for keying); new `characterActivity(frame, prev)` → `Record<charId, "idle"|"thinking"|"speaking">` — trace `speaker` step or `internal_thought` sets **thinking**, first `character_dialogue` chunk sets **speaking**, `done:true` and stream end reset to **idle**); `web/frontend/features/story-player/useScenePlay.ts` (hold `activity` + `activityByChar` state, fold both in `onFrame`, reset `activityByChar` to all-idle when the stream leaves `"streaming"`, expose both; `rehydrateFromHistory` seeds nothing — the pulse is live-only by design).
- **Rationale:** pure state layer, independently testable before any UI consumes it; both Phase 6 surfaces (right rail + cast rail) read from this one source.
- **Tests:** turn-stream unit tests — each mapped trace step/event produces the right entry, feed caps + orders newest-first, `speaker`→thinking, first dialogue chunk→speaking, `done`→idle; `useScenePlay` — activity folds during a scripted stream and statuses reset to idle on stream end.
- **Action:** Run `npm test` (turn-stream, useScenePlay) + typecheck. Once green, commit: `[Chat UX Additions] (5/7) Complete: live activity feed + per-character thinking/speaking state from the turn stream.`
