# Design Quality and Anti-Generic Rules

Use this reference to make web pages feel intentional, project-specific, and human-designed.

## Core Principle

A site looks generated when it feels assembled from defaults: generic gradients, floating cards, abstract icons, vague copy, fake metrics, oversized heroes, and no strong product identity.

Good design shows taste, constraint, specificity, and hierarchy. Every visual choice should connect to the project's purpose, audience, workflow, data, or artifacts.

## Avoid Generic Visual Cliches

Do not default to:

- blue or purple neon gradients
- decorative glassmorphism panels
- abstract glowing orbs
- random mesh backgrounds
- AI brain, network-node, chat-bubble, or sparkle icons
- overly smooth 3D blobs
- generic SaaS dashboard metrics
- perfectly centered hero text with no contextual detail

Use visual elements from the actual domain, workflow, data model, mascot, audience, or interaction model.

## Define Identity Before Pages

Before designing pages, define:

- one primary color
- one secondary color
- one accent color
- neutrals
- one display type direction
- one body type direction
- border-radius logic
- one or two shadow styles
- icon style
- illustration or image style
- spacing scale

A site feels coherent when sections share a system. It feels generated when each section looks independently prompted.

## Make Layouts Less Predictable

Avoid blindly repeating:

```text
hero -> logo cloud -> 3 feature cards -> 3 steps -> testimonial -> CTA
```

Use structure that fits the product:

- annotated screenshot
- workflow map
- comparison table
- timeline
- before/after example
- process diagram
- live demo block
- source/evidence preview
- use-case panel
- dense data table

Every important page should have at least one layout decision that feels specific to the project.

## Use Concrete Product Language

If a sentence could appear on 1,000 other sites, rewrite it.

Replace vague copy with exact workflows, users, objects, and outputs.

```text
Generic: AI-powered insights.
Better: Turn uploaded papers into claim-evidence maps.

Generic: Streamline your workflow.
Better: Plan searches, read sources, extract claims, and assemble reports.

Generic: Built for productivity.
Better: Designed for researchers managing 50+ sources per report.
```

UI labels, cards, empty states, filters, tabs, and buttons should use the project's domain vocabulary.

## Use Meaningful Imagery

Every image should help the user understand something.

Use imagery that:

- explains the product
- shows a workflow
- shows a real interface state
- reveals a real artifact
- supports the brand personality
- clarifies a report, graph, source, dataset, map, or timeline

Avoid imagery that only looks futuristic.

## Prioritize Understanding

The first screen and primary flow should quickly answer:

- What is this?
- Who is it for?
- What problem does it solve?
- What happens first?
- What does the user get at the end?
- Why should the user trust it?

Design should support comprehension before visual flash.

## Use Strong Hierarchy

Each page should have:

- one dominant headline
- one clear supporting message
- one primary action
- one secondary action only when useful
- section headings that explain the section
- cards or panels with distinct purposes

Users should know where to look first, second, and third.

## Do Not Use Cards For Everything

Cards are useful, but not every idea deserves a card.

Prefer the content form that best explains the idea:

- feature cards for peer-level features
- timeline for sequence
- process map for workflows
- comparison table for tradeoffs
- annotated screenshot for interface explanation
- demo block for behavior
- before/after for transformation
- diagram for systems

## Add Specificity Without Mess

Specificity makes UI feel designed.

Use:

- product-specific empty states
- real examples
- custom labels
- domain-aware icons
- subtle texture when appropriate
- annotations
- useful dividers
- realistic screenshots

Avoid sterile placeholder copy such as "No data found" when the domain gives a better explanation.

## Use Color With Restraint

Use mostly neutrals, one recognizable brand color, and accents sparingly.

Reserve saturated color for:

- primary actions
- active states
- warnings
- success states
- highlights
- key illustrations

Avoid rainbow gradients unless the brand truly calls for them.

## Use Typography As Identity

Typography should feel selected, not inherited.

Define:

- display type style
- body type style
- heading weights
- line heights
- responsive scale
- label and metadata treatment

Avoid making every heading huge, bold, centered, and gradient-filled.

## Design Real States

A real product needs:

- loading states
- empty states
- error states
- partial-data states
- success states
- permission states
- mobile states
- long-content states
- dense-data states

Idealized homepages are not enough.

## Avoid Fake Metrics

Do not use unverifiable claims like:

- 98% faster
- 10x productivity
- 1M+ users
- 24/7 AI

Use product-specific examples instead:

- 15 sources collected
- 7 claims extracted
- 3 conflicting findings
- 2 weak citations flagged
- report draft ready
- schema updated from 4 new entities

## Make Components Domain-Aware

Name components and states around the project domain.

For a research tool, use vocabulary such as sources, claims, evidence, reports, citations, hypotheses, validation, gaps, and confidence.

For a healthcare app, use vocabulary such as patients, cases, cohorts, risk, timeline, imaging, notes, findings, and recommendations.

The interface should not sound like generic SaaS unless the product itself is generic SaaS.

## Use Motion Purposefully

Use animation for:

- state changes
- progress
- hierarchy
- process explanation
- activity feedback
- action confirmation

Avoid constant shimmer, floating blobs, infinite gradients, excessive parallax, and cursor-following effects unless the project specifically needs them.

## Make Mobile Designed, Not Collapsed

For mobile:

- reduce hero height
- shorten copy
- avoid unreadable giant screenshots
- collapse complex diagrams into steps
- keep calls to action reachable
- simplify forms
- check real content at small widths

Mobile should feel intentionally designed, not like a compressed desktop page.

## Review Checklist

Before shipping a page, check:

- Could this page belong to any generic AI startup? If yes, redesign.
- Does the copy mention specific workflows, users, outputs, or constraints?
- Does every image explain something real?
- Is there a consistent type, color, spacing, and component system?
- Are gradients and glow effects restrained?
- Does every section avoid using the exact same layout?
- Are loading, empty, error, permission, and mobile states designed?
- Does the site have one memorable motif?
- Is accessibility visibly considered?
- Is anything present that could be copied unchanged into another product? If yes, remove or rewrite it.
