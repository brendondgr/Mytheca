# PROTOCOL — EXP-2026-08-011 Context compaction

> Written **before** the run, per §3.2 of the contract. Nothing in this file was
> edited after seeing a result; anything learned during the run is in `ISSUES.md`.

## Question

When a scene outgrows the model's context window, does folding the dropped beats into a
rolling summary preserve continuity that dropping them outright loses — and does it cost
anything in the writing?

## Hypothesis

Stated ahead of the run, and specific enough to be wrong:

**H1 (continuity).** With compaction on, a late-scene player line referring to a fact
established *before* the verbatim window will be answered consistently more often than with
compaction off.

**H2 (cost).** Compaction adds at most one model call per anchor block (20 beats) and does not
measurably reduce the reusable prompt prefix, because the summary is placed at the head of the
append-only region and therefore changes on the same turns the anchored window re-anchors.

**H3 (writing, the one that would stop the ship).** Compaction does not make the prose worse.
This is the null we most want to be unable to reject: a summary is a compression, and
compressions flatten. If a blinded read prefers arm A, the honest outcome is to leave
`TURN_CONTEXT_COMPACTION` defaulted off and say so.

## Setup

Two arms, **interleaved scene-by-scene inside one process run**. `docs/checklist.md` states
plainly that day-to-day comparison on this endpoint is worthless — the served model has changed
under this project before (`EXP-2026-08-007` ran on `qwen38-27B-awq`, `EXP-2026-08-008` on
`gemma4-26B-mtp`) — so the arms must alternate within a single session or the comparison is
between two days, not two configurations.

| Arm | Configuration |
| --- | --- |
| **A** (control) | `contextPolicy: "fixed"`, `contextBeats: 100`; `TURN_CONTEXT_COMPACTION=false`. Today's behaviour: the oldest beats simply drop. |
| **B** (treatment) | `contextPolicy: "auto"` (fitted window, `services/context_budget`); `TURN_CONTEXT_COMPACTION=true` (`services/history_compaction` + `agents/recap_agent`). |

Both arms play the **same scripted player lines** against the **same generated world**, so the
only difference is what the cast can read.

Real files under test: `web/backend/app/services/context_budget.py`,
`web/backend/app/services/history_compaction.py`, `web/backend/app/agents/recap_agent.py`,
`web/backend/app/agents/character_turn_agent.py` (`_build_user_prompt`'s append-only region).

Entrypoint: `utils/scripts/research/run_context_compaction.py`.

## Data

A world generated by the harness at run time (the same `build_world` helper
`run_conversation_scaling.py` uses), plus a scripted line list written for this experiment.
Nothing is held out and nothing ships with the repository as an evaluation set — this is a
behavioural probe of a running system, not a benchmark, and it must not later be cited as one.

## Metrics

| Metric | Definition | Direction |
| --- | --- | --- |
| `continuity_hits` | Of the scripted **probe** turns (each referring to a fact planted before the verbatim boundary), how many produced a beat containing that fact's key content words, scored by `services/direction_check.coverage ≥ 0.34` against the planted fact. Denominator: number of probes. | higher better |
| `probe_total` | Number of probe turns actually run in the arm. Reported separately so a partial run cannot be read as a rate. | — |
| `prompt_tokens_mean` | Mean `usage.prompt_tokens` over the arm's character calls, from the `context` trace step. | lower better |
| `reusable_prefix_share` | Mean `reusablePrefixChars / promptChars` over the arm's character calls — the share of each prompt byte-identical to the previous one. Tests H2. | higher better |
| `recap_calls` | Number of `compaction` trace steps with `ran: true`. Arm A is 0 by construction; this is the cost side of H2. | — |
| `turn_seconds_mean` | Mean wall-clock per turn. Reported with the caveat below. | lower better |

**A metric this experiment does NOT claim.** No automated score of prose quality. H3 is answered
by a blinded pairwise read of matched beats recorded in `RESULTS.md`, or it is answered "not
measured" — a rubric invented for one run is not evidence.

## Baselines

Arm A *is* the baseline: the behaviour that shipped before this plan. The comparison is fair
because both arms run the same lines against the same world in the same process, and the only
manipulated variable is what the character prompt contains.

## Confounds and how they are handled

- **Endpoint drift.** Handled by interleaving. Also recorded: the served upstream model id, at
  run start, in `manifest.yaml`.
- **Wall-clock.** This machine runs other work; `turn_seconds_mean` is reported but must not be
  used to support any claim on its own. Prefer counts (`recap_calls`, `prompt_tokens_mean`).
  `docs/checklist.md` already records a case where a 66× latency finding was a disconnected GPU.
- **The continuity probe is lexical.** It uses the same coverage check the direction system
  uses, with the same known crudeness. It can under-count a fact recalled in paraphrase. It is
  therefore a *floor* on continuity, not a measurement of it, and the direction of the error is
  the same in both arms.
- **One model.** Everything here runs on whatever the relay serves at run time. A finding on one
  model is a finding on one model (`EXP-2026-08-007`'s own limitation, recorded).

## Stopping rule

Fixed: N scenes per arm, N turns per scene, decided in the harness before the run and recorded
in `manifest.yaml`. No peeking-and-extending.

## What would falsify the hypothesis

- **H1** — arm B's `continuity_hits` rate not exceeding arm A's.
- **H2** — `reusable_prefix_share` materially lower in arm B, or `recap_calls` exceeding
  `ceil(beats / anchor_block)`.
- **H3** — a blinded read preferring arm A.

## Failure handling

**If any arm or scene fails to complete, report per-run rows and NO aggregate.** Survivors of a
partially-failed run are not a random subsample; `EXP-2026-08-001` is this repository's worked
example of getting that wrong and catching it. A failed run keeps its folder, with
`status: failed` and an honest `ISSUES.md`.
